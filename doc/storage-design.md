# 작업 공간 파일 구조 및 저장 방식 설계안

작성일: 2026-11-19

상태: 2026-11-19 사용자 확인으로 파일 분리 방식·개인 저장 이력 보관 위치·세트 저장 검증 정책 확정. 2026-11-20 v1 JSON 스키마·샘플·관계 검증 도구 작성. 실제 파일 저장 구현과 에이전트 계약은 후속 작업이다.

관련 기능: 01.01, 01.06, 01.08, 02.04~02.07, 03~04, 06~09. 에이전트 통신·인증 계약은 02.02~02.03에서 별도로 설계한다.

## 1. 현재 구현에서 확인한 기준

| 대상 | 확인 내용 | 새 설계에 반영할 점 |
| --- | --- | --- |
| React 작업 공간 | `WorkspacePage.tsx`에서 공간별 화면을 유지하고 컬렉션·API·환경·세트·열린 탭·초안을 메모리로 분리 | 현재의 공간별 격리를 파일 원본과 개인 상태에도 적용 |
| React API | `features/workspace/types.ts`의 `SampleRequest`가 API 명세·문서와 현재 세트 값을 함께 표현 | 화면 모델을 그대로 파일에 직렬화하지 않고 명세와 세트 값으로 분리 |
| React 입력 세트 | `features/payload-presets/types.ts`에서 필드 ID로 값·사용 여부를 복사·적용 | 이름이나 배열 위치가 아니라 안정적인 ID로 연결 |
| React 저장 이력 | API 폼 복사본을 메모리에 보관하고 되돌리기는 현재 폼에만 적용 | 파일 원본·API 식별·이름·위치·다른 세트·실행 결과는 자동 변경하지 않음 |
| Vue 저장소 | `model_service/SelfApi.ts`의 `ApiDocDB` 버전 6에 `apiTable`, `folders`, `environmentSetting`, `revisionHistory`, `coverPage` 저장 | 브라우저 원본을 파일 기반 원본으로 직접 간주하지 않고 별도 이전 절차 필요 |
| Vue API 모델 | `model_service/Type.ts`의 요청·응답 명세에 테스트 값·파일·계산용 필드가 혼재 | 명세·입력값·파일 참조·UI 파생값을 구분 |
| Vue 환경 | 환경 모델에 `host`, `authToken`, `isSelected`; 선택 환경을 Pinia persist로 관리 | 공유 환경 템플릿, 개인 실제값, 개인 선택 상태를 분리 |
| Vue 개정 이력 | 버전·변경 내용·작성자·검토자·승인자 등 문서 개정 메타데이터 | React의 API 저장 복사본 이력과 다른 데이터로 취급 |

위 분석은 저장 설계에 필요한 범위다. Vue의 전체 기능 차이·이전 도구·Excel 결과 검증은 01.01과 11.01에서 별도로 확인한다.

## 2. 파일 분리 방식 비교와 권장안

| 방식 | 장점 | 고려할 점 |
| --- | --- | --- |
| 작업 공간 전체를 JSON 하나로 저장 | 초기 구현과 전체 저장이 단순 | 다른 API를 편집해도 같은 파일이 변경되어 Git 충돌 범위가 큼 |
| API별 JSON, API 안에 문서·입력 세트 포함 | API 단위 변경·공유, 명세와 세트를 같은 파일에 저장 가능 | 한 API의 서로 다른 세트를 함께 편집하면 해당 파일에서 충돌 가능 |
| API 명세·문서·각 세트를 모두 별도 파일로 저장 | 개별 세트 변경의 Git 충돌을 줄일 수 있음 | 공통 명세 변경과 세트 갱신에 여러 파일의 일관성 처리가 필요 |

**확정 방식:** 작업 공간 목록 구조는 `workspace.json`, API별 명세·문서·입력 세트는 API별 JSON, 공유 환경은 환경별 JSON으로 저장한다. 개인 설정·초안·저장 이력은 Git 공유 파일에서 분리한다.

아래 구조는 사용자가 선택할 **데이터 작업 폴더**의 구조다. 이번 스키마 작업에서 소스 저장소의 폴더 구조를 변경하거나 실제 작업 폴더를 생성하지 않는다.

```text
사용자가 선택한 작업 폴더/
├── workspace.json
├── apis/
│   └── <api-id>.json
├── environments/
│   └── <environment-id>.json
└── .gitignore
```

- 폴더 이름·파일 역할은 포맷 v1에서 고정한다. 파일명은 이름 대신 UUID를 사용한다.
- API 이름 변경은 API 파일 내용만, 컬렉션·폴더 이동은 `workspace.json`의 위치 정보만 변경한다.
- 최초 폴더 생성 시 기존 파일을 덮어쓰지 않는다. 열기는 명시적인 `workspace.json` 검증을 거친다.
- `.git` 폴더는 API Doc이 생성·수정하지 않는다. Git 초기화·커밋·동기화는 외부 Git 도구로 수행한다.
- 개인 데이터는 작업 폴더에 쓰지 않으므로 `.gitignore`만으로 비밀값 보호를 보장하는 구조에 의존하지 않는다.

## 3. 파일별 책임과 관계

### 3.1 `workspace.json`

| 필드 | 의미·검증 |
| --- | --- |
| `formatVersion` | 정수 `1`. 지원 버전 검증의 기준 |
| `id` | 작업 공간 UUID. 같은 Git 작업 공간에서는 PC 간 유지 |
| `name` | 표시 이름. 파일 경로와 분리 |
| `collections` | 순서가 있는 컬렉션 배열 |
| `collections[].id`, `name` | 컬렉션 식별자와 표시 이름 |
| `collections[].apiIds` | 컬렉션 바로 아래 API의 순서 |
| `collections[].folders` | 순서가 있는 단일 단계 폴더 배열 |
| `folders[].id`, `name`, `apiIds` | 폴더 식별자·표시 이름·API 순서 |
| `environmentIds` | 공유 환경의 표시 순서 |

- 컬렉션·폴더·API ID는 작업 공간 안에서 충돌하지 않는다.
- 각 API는 컬렉션 바로 아래 또는 한 폴더 중 한 위치에만 속한다. 위치 정보를 API 파일에 중복 저장하지 않는다.
- 빈 컬렉션·폴더는 배열 항목으로 유지한다. 현재 React UI와 같이 폴더의 중첩은 지원하지 않는다.
- 참조한 API·환경 파일 누락, 같은 API의 중복 배치, 등록되지 않은 파일을 구분해 안내한다. 누락 파일을 빈 API로 자동 대체하거나 참조 밖 파일을 자동 삭제하지 않는다.
- 향후 중첩 폴더 지원은 명시적인 포맷 변경으로 다룬다.

### 3.2 `apis/<api-id>.json`

| 필드 | 의미·검증 |
| --- | --- |
| `formatVersion`, `id` | 포맷 버전과 파일명에 일치하는 API UUID |
| `name`, `method`, `url` | API 이름·지원 HTTP 메서드·변수 치환 전 URL 원문 |
| `request.path`, `query`, `headers` | 필드 ID·키·타입·필수 여부·설명 등의 API 공통 명세 |
| `request.query[].arrayFormat` | `repeat` 또는 `comma`. 기본값은 명시적으로 `repeat` 저장 |
| `request.body` | 본문 형식과 공통 구조. v1 구현 범위는 현재 UI의 `json`·`multipart` |
| `response.success` | 성공 응답 필드 명세 |
| `response.errors` | 오류 사례 ID·이름·상태 코드 문자열·설명·본문 예시 |
| `documentation` | 일반 텍스트 설명·요청 예시·응답 예시 원문 |
| `defaultPresetId` | 재열기 시 적용할 공유 기본 세트 ID |
| `presets` | 순서가 있는 입력 세트 배열. 최소 한 세트 필요 |

- 각 요청 필드에는 안정적인 ID를 부여한다. Path는 필수·사용 고정이며 Query·Headers·multipart는 중복 키와 행 순서를 보존한다.
- Body·성공 응답의 중첩 구조는 현재 `BodyField`의 `id`, `parentId`, `name`, `type`, `required`, `description` 관계를 유지한다. 부모 존재·순환·같은 부모의 중복 키를 검증한다.
- 타입 표현은 현재 React의 `FieldType`을 기준으로 스키마에 열거한다. `file`은 multipart에만 허용한다.
- 명세에는 실제 입력값·사용 여부를 중복 저장하지 않는다. 오류 응답의 본문 값과 문서 예시는 명세용 예시로 구분한다.
- 상태 코드는 현재 UI와 같이 최대 3자리 문자열이며 400~599 범위 제한을 추가하지 않는다.
- `text`, `urlencoded` 등 추가 본문 형식과 인증·테스트 명세는 해당 기능 도입 전에 포맷에 정의한다. 기존 저장기가 알 수 없는 값을 임의로 변환하지 않는다.

### 3.3 입력 세트

세트는 API 파일의 `presets`에 포함한다. 공유되는 세트 ID·이름·설명과 값만 보관한다.

```json
{
  "id": "preset-uuid",
  "name": "입력 세트 1",
  "description": "기본 조회",
  "values": {
    "path": {},
    "query": {
      "field-uuid": { "enabled": true, "value": "[1, 2, 3]" }
    },
    "headers": {},
    "body": {
      "fields": {},
      "enabled": {}
    },
    "multipart": {}
  }
}
```

- 위 예시의 `*-uuid`는 설명용 표기다. 실제 파일에서는 유효한 UUID를 사용한다.
- 입력값은 편집용 문자열로 저장한다. `0`, `false`, 빈 문자열, JSON 배열을 실행 직전에 명세 타입에 맞게 변환한다.
- 필드 ID가 누락되면 입력값은 빈 문자열, 사용 여부는 `true`로 해석한다. Body의 사용 여부도 같은 규칙을 따른다.
- v1에서는 세트 간 상속을 제공하지 않는다. 빈 값은 빈 값이며 다른 세트의 값을 찾아 채우지 않는다.
- 필드 이름·설명 변경은 세트 값에 영향을 주지 않는다. 타입 변경은 현재 세트의 해당 값을 비우고 다른 세트는 값을 유지하되 적용·저장·실행 시 최신 타입으로 검증한다.
- 명세에서 삭제한 필드의 값은 모든 세트에서 정리해 같은 API 파일에 저장한다. 신규·삭제 필드와 세트 값을 다른 파일로 나눠 저장하지 않는다.
- JSON Body는 공통 구조와 세트별 필드 값을 원본으로 삼고 JSON 문자열은 재구성한다. 편집 보기(`fields`/`json`)는 개인 UI 상태다. 잘못된 JSON 원문은 초안에 보관하며 공유 원본으로 저장하지 않는다.
- multipart 파일 내용·`File` 객체·`selectionId`·절대 파일 경로는 공유 세트에 기록하지 않는다. 파일 행의 ID와 명세만 공유하며 재열기 시 파일 재선택을 안내한다.
- 저장은 공통 명세·문서와 현재 선택 세트의 편집값을 반영한다. 다른 세트의 값은 구조 정리에 필요한 변경 외에는 유지한다.
- 선택 세트와 다른 세트가 새 명세에 맞지 않으면 저장을 막고 해당 세트 이름·필드를 안내한다. 자동 값 변환·조용한 데이터 삭제로 통과시키지 않는다. 현재 UI 저장 검증과 달라지는 부분이므로 실제 저장 연결 전에 구현·검증한다.

### 3.4 `environments/<environment-id>.json`

- `formatVersion`, `id`, `name`, 순서가 있는 `variables`를 저장한다.
- 변수에는 안정적 ID·키·활성 여부·공유할 기본값 또는 비밀값 참조를 저장한다. 중복 키는 허용하지 않는다.
- 선택 환경은 개인 설정이다. Vue의 `isSelected`를 공유 환경 파일로 옮기지 않는다.
- 실제 토큰·비밀번호는 파일에 저장하지 않는다. 환경·세트·헤더·본문·문서 예시에 비밀값을 넣는 경우도 같은 원칙을 적용한다.
- 비밀값은 실행 중 메모리에서 별도 참조로 주입한다. 비밀값을 구분하는 입력 UI와 개인 실제값의 처리 계약은 04.02~04.04에서 정의하며, 해당 구분 없이 기존 UI 값을 일괄 공유 파일로 내보내지 않는다.

## 4. 개인 데이터와 공유 데이터의 저장 책임

| 데이터 | 보관 위치 | 범위·복원 기준 |
| --- | --- | --- |
| API·문서·입력 세트·공유 환경 | 선택한 작업 폴더 | 에이전트가 읽고 저장. Git 공유 원본 |
| 최근 작업 폴더 목록·실제 경로 | 에이전트의 사용자별 앱 데이터 | 사용자 PC 내부에서 관리. 브라우저에는 승인된 연결 핸들을 제공 |
| 테마·레이아웃·선택 공간·환경·열린 탭·편집 보기 | IndexedDB | 브라우저 출처 + 로컬 폴더 연결 ID + 작업 공간 ID로 구분 |
| 저장 전 초안 | IndexedDB | 위 범위 + API ID + 세트 ID. 공통 명세 초안과 세트 입력 초안을 구분 |
| API 저장 이력 | IndexedDB | 해당 PC·브라우저의 개인 이력. API 전체 명세·문서와 저장 당시 선택 세트 값을 보관 |
| 실제 실행 이력·응답 보관 | 08.03에서 확정 | 저장 이력과 별도. 현재 설계로 응답 영구 보관을 시작하지 않음 |
| 토큰·비밀번호·연결 세션 | 기본 메모리 | 공유 파일·IndexedDB 초안·저장 이력·로그에 실제값 기록 금지. 영구 보관은 04.04에서 별도 결정 |
| 브라우저 선택 파일 | 메모리 | 세트·공간 간 분리, 새로고침 후 재선택 |

- Git 복제 시 workspace ID는 같지만 로컬 폴더 연결 ID는 다르다. 동일 작업 공간을 다른 폴더에 복제해 열어도 초안을 자동으로 섞지 않는다.
- 같은 출처의 여러 웹 탭은 동시에 같은 파일을 저장할 수 있으므로 파일 버전 검사를 반드시 거친다. 초안에는 편집 세션 ID를 포함해 다른 웹 탭의 초안을 조용히 덮어쓰지 않는다.
- IndexedDB는 복원 보조 데이터다. 파일 저장 확인 전에 초안만 지웠거나 저장 완료로 표시하면 안 된다.
- 비밀값을 마스킹한 문자열 `***`를 실제 값으로 복원하지 않는다. 비밀 참조와 미입력 상태를 데이터에서 구분한다.

## 5. 저장·복원·충돌 처리 흐름

1. 에이전트가 사용자가 승인한 폴더의 manifest와 참조 파일을 검증한다. 지원 버전·ID·필수 필드·참조·순서를 확인한다.
2. UI는 읽은 파일 내용과 파일별 내용 해시를 저장 기준으로 보관한다. 현재 편집 상태와 저장 기준을 구분한다.
3. 저장 시 명세·문서·세트 구조 및 값을 검증하고 공유 가능한 데이터만 구성한다. 비밀값과 로컬 파일 실체는 별도 상태에 남긴다.
4. 에이전트는 공간별 쓰기를 직렬화하고, 파일 변경 직전 기대 해시와 디스크의 현재 해시를 비교한다. 불일치하면 충돌로 반환하고 파일을 덮어쓰지 않는다.
5. 단일 API 수정은 해당 JSON 하나로 저장한다. 같은 디렉터리의 임시 파일에 쓴 뒤 교체하며, 실패 시 기존 원본을 보존하고 UI 초안도 유지한다. Windows의 파일 점유·디스크 오류·교체 실패는 02.05에서 검증한다.
6. API 추가·삭제처럼 manifest와 API 파일이 함께 변경될 때는 복구 저널·기존 내용·기대 해시를 에이전트 개인 앱 데이터에 기록한다. 재시작 시 미완료 작업을 탐지하고 검증 후 완료 또는 복구한다. 외부 Git 도구까지 포함한 다중 파일 원자성을 보장한다고 표시하지 않는다.
7. 전체 저장 완료 응답을 받은 뒤에만 UI 저장 기준을 갱신한다. 저장 중 추가 편집이 발생했다면 실제 저장한 복사본까지만 기준을 갱신하고 이후 편집은 미저장으로 남긴다.
8. 성공한 저장 복사본을 개인 저장 이력에 추가한다. 파일은 저장됐지만 IndexedDB 이력 기록이 실패한 경우 두 결과를 구분해 안내하고 파일 저장을 자동 반복하지 않는다.
9. 이력 되돌리기는 현재 폼의 명세·문서와 현재 선택 세트의 값만 변경한다. 미저장 덮어쓰기는 확인하며, 다른 세트·파일 원본·실행 결과는 자동 변경하지 않는다. API 이름·위치는 현재 값을 유지한다.
10. 파일 외부 변경은 초안의 기준 해시와 비교한다. 초안이 없으면 재조회하고, 초안이 있으면 새 원본 확인·편집 유지 후 수동 조정 흐름을 제공한다. 삭제·Git pull·동시 저장을 자동 병합하거나 자동 재저장하지 않는다.

복구 저널의 크래시 시점별 동작, 연결 핸들, 저장 요청 중복 방지, 폴더 접근 승인·심볼릭 링크 처리, 비밀값 주입은 후속 에이전트 설계에서 구체화한다. 이 문서만으로 02 단계 완료를 표시하지 않는다.

## 6. 포맷과 Git 변경 규칙

- 파일은 UTF-8, BOM 없음, 들여쓰기 2칸, LF 줄바꿈과 마지막 개행을 사용한다.
- 객체 필드는 스키마에서 정한 순서로 출력하고, 필드 ID를 키로 하는 값 맵은 ID 오름차순으로 출력한다. 배열은 사용자 표시·실행 순서를 보존한다.
- 출력에서 `undefined`, 브라우저 객체, 실행용 자동 헤더·변수 치환 결과를 제외한다. 저장할 때마다 바뀌는 시각은 공유 파일에 추가하지 않고 개인 저장 이력에 기록한다.
- v1의 선택 필드는 스키마 기본값에 따라 읽고 쓰는 규칙을 고정한다. 같은 내용을 반복 저장했을 때 파일 바이트가 바뀌지 않아야 한다.
- 미지원 포맷 버전과 알 수 없는 필드는 손실 방지를 위해 쓰기를 차단하고 안내한다. 자동 마이그레이션·자동 버전 낮추기를 수행하지 않는다.
- 형식 변경은 별도 마이그레이션과 원본 백업을 거친다. 작업 공간·API·환경 파일은 같은 v1 계약으로 검증한다.

## 7. 실제 구현 전에 확인할 기준

- JSON → 화면 → 저장 → 재열기에서 명세·문서·모든 세트·순서가 유지된다.
- 이름 변경·폴더 이동 후 API/세트/필드 ID와 값 연결이 유지된다.
- Query·Headers 중복 키, 배열, 한글, `0`·`false`·빈 값·null·중첩 Body를 왕복 보존한다.
- 명세 삭제·타입 변경으로 영향을 받는 다른 세트를 명시하고 유효하지 않은 값의 자동 변환을 방지한다.
- 잘못된 JSON·포맷 버전·누락 참조·외부 변경·쓰기 실패 시 원본과 초안이 보존된다.
- 저장 중 후속 편집·응답 유실·이력 기록 실패를 구분한다. 다중 파일 작업은 단계별 강제 종료 후 복구를 검증한다.
- 실제 비밀값과 파일 내용·절대 경로가 공유 파일·초안·저장 이력·로그에 포함되지 않는지 확인한다.
- Git 복제본과 다른 웹 탭의 개인 상태가 섞이지 않고, 최신 파일 형식에 모르는 필드가 있으면 쓰기가 차단된다.

## 8. 사용자 확인으로 확정한 결정

1. **파일 분리:** `workspace.json` + API별 JSON(문서·세트 포함) + 환경별 JSON 구조를 사용한다.
2. **개인 저장 이력:** Git 공유에서 제외하고 IndexedDB에 보관한다. 새 PC·다른 브라우저·사이트 데이터 삭제 후에는 개인 이력이 이어지지 않는다. API 원본의 팀 변경 이력은 외부 Git에서 관리한다.
3. **세트 저장 검증:** 공통 명세 변경으로 다른 세트에 오류가 생기면 해당 세트를 안내하고 저장을 차단한다. 자동 변환 대신 해당 세트를 수정한 후 저장한다.

확정된 방향의 정식 JSON 스키마·샘플은 아래에 정의한다. 에이전트 저장 인터페이스와 개인 저장 이력의 보관 개수·용량·정리 정책은 해당 구현 전에 별도로 확정한다. 이번 검증에는 이미 설치된 개발 의존성을 활용하며 라이브러리를 추가하지 않는다.

### 스키마를 읽는 규칙

- 스키마 루트는 세 문서 중 하나만 허용한다. 실제 파일 검증에서는 파일 경로에 맞는 `#/definitions/workspace`, `#/definitions/api`, `#/definitions/environment`를 선택한다. 잘못된 위치에 다른 종류의 문서를 저장할 수 없다.
- 정의된 객체 필드는 모두 필수다. `value`/`secretRef`처럼 아래에서 선택으로 설명한 속성만 예외다. 사용하지 않는 목록·값 맵·설명·예시도 빈 배열·객체·문자열로 명시한다. 스키마 검증기가 값을 자동 추가·삭제·변환하지 않는다.
- 모든 객체는 정의되지 않은 속성을 거부한다. 값 맵의 키는 필드 UUID로 제한한다. 미지원 `formatVersion`은 거부한다.
- UUID는 소문자 8-4-4-4-12 형식, 버전 1~8·RFC variant 비트를 허용한다. 새 데이터는 `crypto.randomUUID()`의 v4를 사용한다. 최상위 문서·컬렉션·폴더 ID는 공간 전체에서, API 내부 필드·세트·오류 사례 ID는 해당 API 안에서 고유하다. 환경 변수 ID는 해당 환경 안에서 고유하다. 같은 이름·중복 키의 허용 여부와 ID 고유성은 별개다.
- 이름은 공백만으로 구성될 수 없다. 같은 위치의 컬렉션·폴더·API 이름, 같은 API의 세트 이름, 환경 이름은 앞뒤 공백과 대소문자를 무시해 중복 검사한다. 환경 변수 키는 대소문자를 구분하며 비활성 변수를 포함해 중복을 거부한다.
- Path 명세는 `required: true`이며 값 맵에서 사용 해제할 수 없다. Query의 `arrayFormat`은 스칼라 필드에도 `repeat`를 명시하되 배열일 때만 사용한다.
- `request.body`에는 `format`, `json`, `multipart`가 항상 존재한다. `json`은 중첩 필드 배열, `multipart`는 multipart 명세 배열이다. 두 형식의 명세와 편집값을 각각 보존하고 `format`으로 실행 대상을 선택한다.
- Body·성공 응답 구조는 빈 배열 또는 첫 항목이 `name: "$"`, `parentId: null`인 유일한 루트를 가진 필드 배열이다. 객체 아래 키만 같은 부모 안에서 고유해야 하며, 배열 자식은 배열 내 표시 순서로 조립한다. `object array`의 자식은 `object`만 허용한다. 스칼라·단일 타입 배열에는 자식 필드를 두지 않는다.
- 오류 응답 `status`는 현재 UI와 일치하게 최대 3문자 문자열이며 빈 값도 허용한다. 오류 사례 예시 편집값이므로 400~599 범위 검사를 하지 않으며 실제 HTTP 응답 코드 검증과 구분한다.

### 값과 비밀 참조의 정확한 형식

| 위치 | 허용 값 |
| --- | --- |
| 세트 `values.path/query/headers` | `{ "enabled": true, "value": "입력 원문" }` 또는 `{ "enabled": true, "secretRef": "비밀 참조 UUID" }` |
| 세트 `values.body.fields` | 스칼라·단일 타입 배열 필드 ID에 대응하는 문자열 또는 `{ "secretRef": "비밀 참조 UUID" }`. 컨테이너 값은 저장하지 않음 |
| 세트 `values.body.enabled` | 루트·컨테이너·스칼라 필드 ID에 대응하는 boolean |
| 세트 `values.multipart`의 텍스트 행 | 일반 세트 셀과 같은 `enabled` + `value` 또는 `secretRef` |
| 세트 `values.multipart`의 파일 행 | `{ "enabled": true }`만 허용. 값·파일명·선택 ID·경로·파일 객체를 저장하지 않음 |
| 환경 변수 | `id`, `name`, `enabled`와 `value` 또는 `secretRef` 중 정확히 하나 |

- `secretRef`와 실제 `value`를 함께 기록할 수 없다. 참조 UUID는 공유 가능한 식별자이며 실제 비밀값의 존재·유효성은 이 스키마로 확인하지 않는다.
- 이 형식은 **선언된** 비밀 참조·파일 필드의 직렬화를 제한한다. 임의 문자열이 비밀값인지 자동 판별하는 도구는 아니며, 기존 UI를 파일 저장에 연결하기 전에 비밀값 구분·주입 계약을 구현해야 한다.
- 값 맵 항목이 없으면 빈 문자열·활성 상태로 해석하되 `null` 타입 값은 JSON null로 해석한다. 필수 리터럴이 없으면 저장 오류다. 비활성 필드와 비활성 부모의 하위 값은 보존하면서 리터럴 검증에서 제외한다.
- 모든 세트의 활성 Path·Query·Headers와 현재 Body 형식의 활성 값을 검사한다. 비활성 Body 형식의 명세·값 참조 관계는 검사하되 편집 중인 리터럴 타입은 검사하지 않는다.
- 리터럴 숫자·불리언·단일 타입 배열은 현재 UI와 같은 JSON 표현으로 타입을 검증한다. 필수 Query의 빈 배열은 거부한다. 선택 숫자·불리언의 빈 값은 미설정으로 허용한다.
- `{{변수}}`를 포함한 원문과 `secretRef`는 그대로 유지한다. 변수 해석·우선순위·누락 변수와 주입 후 타입 검사·필수 파일 선택 검사는 04~05 단계에 연결한다. 파일 바이너리를 공유 파일에 넣지 않으므로 재열기 후 필수 파일을 다시 선택해야 하며, 공유 포맷 검증이 실행 준비 완료를 의미하지 않는다.
- 알려지지 않은 필드 ID의 값, 기본 세트 누락, 같은 API의 복수 위치 배치, 파일 누락·ID 불일치·manifest 밖 JSON 파일은 구분된 오류로 반환한다. 어떤 경우에도 파일을 자동 생성·삭제·이동하지 않는다.

### 확인 범위

정상 샘플은 빈 공간, JSON 객체·스칼라·null·혼합 배열 루트, 객체 배열, 복수 세트, 비활성 Body 값, 중복 Query·Headers·multipart 키, `0`·`false`·빈 값·한글, 문서·같은 코드의 복수 오류 사례, 파일 명세·비밀 참조를 포함한다. 오류 샘플은 버전·알 수 없는 속성·ID·참조·부모 순환·중복 키·기본 세트·다른 세트의 타입 오류 등을 확인한다.

이 검증은 스키마와 파싱된 문서 관계·리터럴 값 및 JSON 왕복에 대한 확인이다. React 화면↔저장 모델 변환, 실제 디스크 저장·읽기·복구·충돌, 비밀값 주입, 실제 HTTP 실행은 이번 작업의 완료 범위에 포함하지 않는다. 01.06의 파일 규격을 근거로 후속 단계에서 별도 검증한다.
