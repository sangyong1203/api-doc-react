# Electron PC 앱 및 개인 데이터 저장 설계

작성일: 2026-11-20

상태: 사용자 확인으로 Electron PC 앱, 공유 JSON 파일, 개인 데이터의 `node:sqlite` 저장 방향 확정. 앱 실행 기반·IPC·DB·설치 파일은 아직 구현하지 않았다.

관련 기능: 01.03~01.05, 01.08, 02.01~02.08, 05.01, 08.03, 11.03~11.05.

## 1. 실행 구조

- 사용자는 Windows에 앱을 설치하고 아이콘으로 독립 창을 실행한다. React UI와 Electron 내부 기능은 한 앱으로 배포·업데이트한다.
- 기존 React·TypeScript·Vite UI와 [공유 저장 포맷 v1](storage-design.md)을 재사용한다.
- Renderer는 화면·편집 상태를 담당한다. 파일·DB·대상 API 네트워크 처리는 Node.js를 사용하는 앱 내부 계층이 담당한다.
- Preload는 `contextBridge`로 작업별 API만 제공한다. Renderer에 Node.js·SQL·임의 경로 접근·범용 IPC 호출을 노출하지 않는다.
- 패키징된 앱은 내장 UI를 로드한다. 개발용 Vite 서버와 배포 앱 실행을 구분한다. 사용자가 별도 웹사이트·에이전트를 실행하거나 포트·페어링을 설정하는 과정은 없다.
- Windows를 우선 지원하며 macOS는 후속 범위다. 경로·파일 선택·자격 증명·설치 등 OS 처리는 공통 도메인 코드와 구분한다.

## 2. 런타임과 의존성

- 개발 환경은 Node.js 24 최신 패치를 기준으로 전환한다. 현재 설치·검증된 환경은 22.15.0이며, 실제 업그레이드는 별도 작업이다.
- Electron 안정판의 정확한 버전은 도입 시 지원 상태와 내장 Node를 확인하고 고정한다. 개발 PC의 Node와 Electron 내장 Node는 별개다.
- 개인 DB에는 Electron 내장 `node:sqlite`를 사용한다. 외부 SQLite 네이티브 모듈을 추가하지 않으므로 해당 모듈의 ABI 재빌드가 필요하지 않다.
- Node 24 공식 문서에서 `node:sqlite`는 Stability 1.2(Release candidate)다. 필요한 API가 선택한 Electron에 포함돼 있는지 실제 런타임과 설치본에서 검증한다.
- 패키징 도구·정확한 의존성 버전·앱 코드의 폴더 배치는 실행 기반 구현 시 확정한다. 이번 설계 작업에서는 설치나 폴더 생성을 수행하지 않는다.

## 3. 데이터 소유권

| 데이터 | 저장 위치 | 책임 |
| --- | --- | --- |
| API 명세·문서·모든 입력 세트·공유 환경 템플릿 | 선택한 작업 폴더의 JSON | Git 공유 원본. 포맷 v1 유지 |
| 최근 작업 폴더와 실제 경로 | 앱 사용자 데이터 폴더의 SQLite | 같은 workspace ID를 가진 복제 폴더도 `localFolderId`로 구분 |
| 테마·레이아웃·선택 공간/환경·열린 탭·편집 보기 | 같은 SQLite | 앱 전역 설정과 작업 공간별 설정 구분 |
| 미저장 초안 | 같은 SQLite | 로컬 폴더·작업 공간·API·입력 세트·편집 세션별 격리 |
| API 저장 이력 | 같은 SQLite | 성공한 저장 당시의 명세·문서·선택 세트 값. Git 공유 제외 |
| 개인 실행 이력 | 같은 SQLite | 저장소만 확정. 응답 보관 범위·기간·용량은 08.03에서 정의 |
| 인증 토큰·비밀번호·선택한 업로드 파일 실체 | 기본 메모리 | DB·초안·저장 이력·공유 파일·로그에 실제 비밀값 및 파일 내용 기록 금지 |

- SQLite는 `app.getPath('userData')` 아래 앱 전용 위치에 둔다. 설치 디렉터리·작업 폴더·Git 저장소에 두지 않는다. 일반 DB 파일을 비밀값 보관소로 취급하지 않는다.
- 전역 설정에는 작업 공간 키를 강제하지 않는다. 작업 공간별 상태는 `localFolderId` + workspace ID, API별 상태는 API ID, 세트별 값은 preset ID를 추가한다.
- 저장 이력은 API 전체 명세·문서와 저장 당시 선택 세트 값을 보관한다. 되돌리기는 현재 폼과 현재 선택 세트에만 적용하며 API 이름·위치·다른 세트는 유지한다. 원본 반영에는 저장이 필요하다.
- SQLite는 개인 데이터의 영구 저장소다. 공유 원본은 JSON이며, DB 초안이나 이력만 저장됐다고 API 파일 저장 완료로 표시하지 않는다.

## 4. 접근 경계와 처리 방식

- `contextIsolation`·sandbox를 사용하고 Renderer의 `nodeIntegration`을 끈다. 외부 응답·문서 내용은 실행 가능한 앱 코드로 로드하지 않는다.
- IPC는 호출 화면·작업 종류·입력 타입·데이터 크기·열린 작업 공간을 검증한다. UI는 임의 SQL이나 파일 경로 대신 작업 공간 핸들·API/세트 ID와 필요한 값만 전달한다.
- 폴더는 네이티브 선택창으로 열고 내부에서 실제 경로와 핸들을 관리한다. 앱 재실행 시 최근 폴더 경로·파일 포맷·접근 권한을 다시 확인한다. 경로 이탈·심볼릭 링크·junction·외부 파일 충돌 처리는 실제 파일 계층에서 검증한다.
- DB 연결과 쓰기 소유자를 하나로 관리한다. 이력 적재·정리 등 동기식 SQLite 작업이 창 응답성을 막지 않도록 DB 전용 Worker에서 처리하고 결과를 IPC로 전달한다. Renderer에서 직접 DB에 접근하지 않는다.
- 개인 데이터 변경은 SQLite 트랜잭션으로 묶되, JSON 파일 저장과 SQLite는 하나의 원자적 트랜잭션이라고 가정하지 않는다. 파일 저장 성공과 이력 기록 실패를 구분하고 자동으로 파일 저장을 반복하지 않는다.
- 외부 Git 편집·앱 중단에 대비해 JSON 기대 해시·공간별 쓰기 직렬화·임시 파일 교체·다중 파일 복구 저널을 유지한다. 구체적인 IPC 타입과 복구 단계는 구현 전에 정의한다.
- 시각은 ISO 8601 UTC로 저장하고 UI는 공통 util로 `YYYY-MM-DD HH:mm:ss`를 표시한다.

## 5. 구현 전 세부 결정과 검증

다음 항목은 아직 완료되지 않았다.

1. 정확한 Electron/Node 버전, 패키징 도구, 앱 코드 배치와 IPC 타입.
2. DB 테이블·스키마 버전·트랜잭션, 업그레이드 전 백업과 마이그레이션 실패 시 원본 보존. 미지원 상위 DB 버전은 자동 초기화하지 않고 쓰기를 차단한다.
3. 이력·초안의 보관 개수·용량·기간, 삭제·내보내기·초기화 범위와 백업·복구 절차. 열린 DB는 안전한 백업 API 또는 연결 종료 절차로 복사한다.
4. 앱 재실행 후 설정·탭·초안·이력 복원, 작업 공간 복제본 격리, 파일 저장과 이력 기록의 부분 실패 검증.
5. Windows 설치본에서 `node:sqlite` 로드·읽기/쓰기·트랜잭션·강제 종료 복구·권한/디스크 오류·업데이트 후 데이터 보존 검증.

문서 확정만으로 02.07 또는 실제 저장 기능을 완료로 표시하지 않는다. 현재 UI는 메모리 기반이며 개인 설정·테스트 UI와 문서 UI 검증은 별도 후속 작업이다.
